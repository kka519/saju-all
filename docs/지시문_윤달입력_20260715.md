# 지시문 — 달력 선택에 음력 윤달 추가 (2026-07-15)

## 착수 조건

**couple-match 상대방 입력 작업이 커밋된 후 시작할 것.** 같은 파일(SajuForm, orders/create, orders/confirm, database.ts)을 수정하므로 겹치면 충돌한다.

## 배경

윤달에 태어난 고객은 현재 입력이 불가능하다 — 음력으로 넣으면 평달로 계산되어 명식 전체가 틀어진다(월주부터 오류).

luckyloveme API는 윤달을 정식 지원한다(운세위키_API_가이드.md §3): `calendarType: "음력"` + `isLeapMonth: true`. 코드도 `BirthInfo.isLeapMonth` 타입까지는 있으나 `route-adapters.ts:75` 주석대로 DB 필드가 없어 false 고정 상태. 이번 작업은 그 끊긴 배선을 잇는 것.

## 핵심 설계

- **데이터 모델**: `calendar` enum('solar','lunar')은 유지하고 `is_leap_month boolean` 별도 컬럼. 윤달은 음력의 하위 케이스이고 API도 별도 boolean으로 받으므로 enum에 제3값 추가하지 않는다
- **UI**: 달력 버튼 3개 — [양력] [음력] [음력 윤달]. "음력 윤달" 선택 = 내부적으로 `calendar: "lunar"` + `isLeapMonth: true`
- **유효성 검증(중요)**: 윤달은 특정 연월에만 존재. 없는 연월에 윤달 선택 시 결제 후 API 실패 → mock 폴백 → 틀린 결과 발행 위험. **결제 전(클라+서버) 검증 필수**

## 작업 항목

### 1. 윤달 유효성 검증 유틸

- `korean-lunar-calendar` npm 패키지 도입(KARI 기반, 1000~2050 지원, 의존성 없음·수 KB) 또는 동급 검증 수단
- `src/lib/saju/lunar-validation.ts` 신설: `isValidLunarDate(year, month, day, isLeapMonth): boolean`
  - 윤달 여부뿐 아니라 음력 날짜 자체 유효성(음력 30일이 없는 달 등)도 함께 검증
- **직접 윤달 테이블을 손으로 하드코딩하지 말 것** — 오류 위험. 라이브러리 사용 또는 라이브러리로 생성한 테이블을 스크립트 출처 주석과 함께 커밋
- 단위 테스트: 1984년 윤10월 존재(API 가이드 예시), 1971년 윤5월 존재, 윤달 없는 연도(예: 1985) 거부, 음력 날짜 범위 초과 거부

### 2. DB 마이그레이션 (`0011_leap_month.sql`)

```sql
alter table public.saju_inputs
  add column is_leap_month boolean not null default false,
  add column partner_is_leap_month boolean;
```

(partner_*는 couple-match와 동일하게 nullable — 비궁합 상품은 null)

### 3. 폼 — `SajuForm.tsx`

- 달력 버튼 3개로 교체: 양력 / 음력 / 음력 윤달 (본인·상대방 섹션 동일 적용)
- 상태는 `calendar` + `isLeapMonth`로 분리 관리 (버튼 하나가 두 값을 세팅)
- 클라 검증: 음력(평달/윤달) 선택 시 `isValidLunarDate`로 submit 전 확인, 실패 시 toast — 윤달인데 해당 연월에 윤달 없음: "선택하신 연월에는 윤달이 없어요. 평달인지 다시 확인해 주세요" 톤

### 4. 주문 API — `orders/create/route.ts`

- zod: 본인·partner 스키마에 `isLeapMonth: z.boolean().optional().default(false)`
- **서버 검증**: `calendar === "lunar"`이면 `isValidLunarDate` 통과 못 하면 400 (양력인데 isLeapMonth true면 false로 강제)
- `saju_inputs` insert에 `is_leap_month` / `partner_is_leap_month` 매핑

### 5. 어댑터 연결

- `orders/confirm/route.ts`의 `toBirthInfo`(본인·상대방 양쪽): `isLeapMonth: input.is_leap_month` 매핑 — 페이로드는 `{...birthInfo, fields}` 스프레드라 자동 전송됨
- `route-adapters.ts`의 SajuInputRow 어댑터: false 고정 제거, 실제 값 매핑. 75행 주석 삭제
- `saju/interpret/route.ts`(데모): birthInfoSchema에 이미 `isLeapMonth` 옵셔널 존재 — 서버 윤달 유효성 검증만 추가
- `types/database.ts` 갱신

### 6. 확인 필요 — 자미두수·mock 경로

- `birthInfoToZiweiInput` / `computeZiweiForSlug`가 음력·윤달 입력을 어떻게 처리하는지 확인. 윤달 미지원이면 **조용히 틀린 명반을 만들지 말고** 해당 케이스 처리 방침을 주석으로 명시하고 보고할 것 (수정 범위가 크면 이번 커밋에서 제외하고 보고만)
- mock 폴백(`computeMyeongsik`)의 음력 처리도 동일 — 기존 한계면 한계라고 주석·보고

### 7. 테스트·검증 체크리스트

- [ ] 1984-10-15 음력 윤달 남성 14:30 (API 가이드 예시) → luckyloveme 정상 응답, 명식 생성
- [ ] 같은 날짜를 평달로 넣었을 때와 **월주가 다르게 나오는지** 비교 (윤달 반영의 실질 증거)
- [ ] 윤달 없는 연월 + 윤달 선택 → 폼 차단 + API 400 (결제 도달 불가)
- [ ] 양력 + isLeapMonth true 변조 요청 → 서버가 false로 정규화
